# Next Learning Paths

Use this only after the learner passes the P10 portfolio readiness review, or when they explicitly ask to plan beyond the core path.

## Graduation review

Summarize evidence rather than lesson attendance:

- strongest independent project and what the learner personally implemented;
- frontend, backend, data, testing, operations, and communication strengths;
- remaining risks that would matter in real work;
- kinds of tasks the learner can now complete independently;
- two or three credible next directions.

Do not claim the learner is job-ready solely because every lesson is marked passed. Base the judgment on the project rubric, unfamiliar-code work, debugging, and the learner's ability to explain tradeoffs.

## Let the learner control the fork

Ask one short question: do they want to choose the next direction, or should the mentor design it from their goals and evidence?

If the learner chooses, help them compare only the relevant options. If they delegate, select a path using:

1. career goal and target role;
2. demonstrated weak spots and strengths;
3. project evidence and genuine interests;
4. local job or project needs when the learner provides them;
5. prerequisite value and opportunity cost.

Explain why the chosen path comes next, what is deliberately deferred, and what concrete outcome will prove completion.

## Candidate specializations

- **Frontend depth:** advanced TypeScript, design systems, accessibility, performance, browser internals, and frontend architecture.
- **Backend depth:** Go service design, distributed systems, messaging, caching, profiling, resilience, and API evolution.
- **Data depth:** PostgreSQL internals, schema evolution, analytics, data pipelines, and reliability.
- **Platform/DevOps depth:** cloud fundamentals, infrastructure as code, Kubernetes operations, GitOps, observability, SRE, security, and cost control.
- **Security:** secure design, threat modeling, application security testing, identity, dependency and supply-chain security.
- **Quality engineering:** test strategy, contract and property testing, performance testing, CI reliability, and production verification.
- **Team engineering:** code review, technical writing, estimation, incident collaboration, architecture decisions, and maintaining existing systems.

These are examples, not a fixed menu. Propose another path when the learner's goal supports it.

## Design the continuation

Create the next plan as a small extension, not another giant curriculum dump:

- define the target role or capability;
- identify prerequisites already proven and gaps to close;
- propose the next 2–4 milestones;
- give each lesson a stable ID continuing from `S1-L01` or a clearer specialization prefix;
- require hands-on artifacts and the same quiz gate unless the learner explicitly asks for a different assessment model;
- end with one realistic capstone and an evidence-based review.

Append the selected path, rationale, first milestone, and gate state to `fullstack-learning/progress.md`.
